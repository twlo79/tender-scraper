### 問題 9（新診斷）：`_extract_dates()` 只認民國格式，西元格式 `date` 一律被判定為「無法解析」而放行日期窗

- **現象**：`is_within_date_window()`（`scraper.py:1009`）在候選日期為空時回傳 `True`（放行），原意是給「日期真的抓不到」的情況一個保底。但 `_extract_dates()`（`scraper.py:999-1006`）的正規表示式 `r"\b(1\d{2})[/\-.年](\d{1,2})[/\-.月](\d{1,2})"` **只匹配民國三位數年份**，對西元格式的 `date` 欄位（如 `"2026/06/24"`、`"2026-08-17"`）完全比對不到——實測驗證：
  ```
  _extract_dates("2026/06/24") -> []
  _extract_dates("115.6.25~115.7.9") -> [2026-06-25, 2026-07-09]   # 民國格式可以
  _extract_dates("2026-08-17") -> []
  ```
  也就是說，`date` 欄位「有值但格式是西元」的項目，會被當成「date 為空」一樣直接放行，不管實際公告日期距今多久。全庫 835 筆中受影響筆數：
  | 來源 | 受影響筆數 | 佔該來源比例 |
  |---|---|---|
  | Google Alerts | 207 | 84.1%（207/246） |
  | 國家住宅及都市更新中心 | 24 | 53.3%（24/45） |
  | 國營台鐵 | 19 | 55.9%（19/34，主要是 `date` 欄位另外填入的西元格式項目，非標題內嵌的民國格式） |
  | 農業部 瑠公管理處 | 17 | 94.4%（17/18） |
  | **合計** | **267** | **32.0%（267/835）** |
  這解釋了為何「一、狀況總覽」項目 7 的重放測試會有 71 筆（而非過去幾天報告中的 20 幾筆）通過篩選——多數是舊聞因日期格式不被辨識而被誤判為「放行」，並非篩選範圍突然變寬。
- **定位**：`scraper.py:999-1006`（`_extract_dates()`）。
- **建議修法**（新增一組西元格式的正規表示式，與既有民國格式並存）：
  ```diff
       # 民國：115-05-12、115/05/12、115.05.12、115年05月12日
       for m in re.finditer(r"\b(1\d{2})[/\-.年](\d{1,2})[/\-.月](\d{1,2})", text):
           try:
               found.append(date(int(m.group(1)) + 1911, int(m.group(2)), int(m.group(3))))
           except ValueError:
               pass
  +    # 西元：2026-08-17、2026/08/17、2026.08.17
  +    for m in re.finditer(r"\b(19|20)\d{2}[/\-.](\d{1,2})[/\-.](\d{1,2})\b", text):
  +        try:
  +            found.append(date(int(m.group(0)[:4]), int(m.group(2)), int(m.group(3))))
  +        except ValueError:
  +            pass
       return found
  ```
  （沿用既有函式風格，新增段落與民國格式段落互不影響；`m.group(0)[:4]` 直接取字串開頭 4 碼年份，避免重新設計 group 編號）
- **是否已修**：未修。本次診斷純粹基於程式碼邏輯與 `state.json` 快取的交叉比對驗證（`_extract_dates()` 為純函式、無需連網即可在本地驗證），**建議優先於問題 1/7 等需要連網的問題處理**，因為這是本次唯一不需要網路權限即可完成「定位＋驗證」的問題，且影響範圍最廣（32% 快取）。

- **預期效果**：讓日期窗檢查對西元格式的 `date` 欄位真正生效，減少舊聞被誤判為「無法解析→放行」的機率，尤其能收斂 Google Alerts（受影響比例最高，84.1%）的雜訊。
