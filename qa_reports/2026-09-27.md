## 二、異常與處理

### 問題 A（重新發現，長期擱置後從追蹤清單消失）：`log_checker.py` 讀取 GitHub Actions log 未指定編碼，`daily_report.json` 自建立以來（30 天全部歷史記錄）從未正確解析過任何一天資料
- **現象**：本次逐日核對 `daily_report.json` 全部 30 筆歷史記錄（08-28～09-26），**每一筆 `sources` 皆為 `{}`、`total_new`/`total_pushed` 恆為 0**，即使當日 `sent_log.json` 明確顯示有新增或推播（例如 09-26 `sent_log.json._summary` 顯示 `total_new=5`，`daily_report.json` 該日卻是 `total_new=0`）。
  - 這個 bug 曾在 09-09～09-22 報告中連續追蹤 14 天（編號「問題 7」），但自 09-23 起的報告未再提及、也未見任何修復 commit——追蹤清單本身出現斷點，本次視為「重新發現」提醒後續建立防止追蹤項目無故消失的機制（例如固定待辦清單需逐項標記「已解除」才能移除，而非任由天數推移後靜默漏列）。
- **定位**：`log_checker.py:46-49`（`get_latest_log()`）：
  ```python
  r = requests.get(
      f"https://api.github.com/repos/{GITHUB_REPO}/actions/jobs/{jobs[0]['id']}/logs",
      headers=GH, timeout=30, allow_redirects=True,
  )
  return r.text
  ```
  GitHub job log 端點回應 `Content-Type: text/plain`（無 charset），`requests` 依 RFC 舊規範預設以 `ISO-8859-1` 解碼 `.text`，導致內容原本的 UTF-8 中文多位元組序列被逐 byte 拆成錯誤碼位（`apparent_encoding` 正確偵測為 `UTF-8-SIG`，代表原始位元組本身沒問題，純粹是解碼階段錯誤）。這讓 `parse_log()` 裡所有依賴中文字面比對的 regex（`抓取：`、`合計新增：`、`推播：`）全數失配，只有純 ASCII 的 `WARNING`/`ERROR` regex 不受影響（故 `errors` 欄位偶爾仍有內容，但內容本身也是亂碼）。
- **本次實測驗證（用 run #123 的真實 job log 重放）**：
  - 不修正編碼：`get_latest_log()` 原樣邏輯 → `daily_report.json` 該日會寫入 `sources={}`、`total_new=0`（與現存 09-26 記錄一致）。
  - 加一行 `r.encoding = "utf-8"` 後重放 `parse_log()`：正確解析出全部 13 個來源，且 `total_new=5`、`total_pushed=0`，與 `sent_log.json._summary` 完全吻合。
- **建議修法**：
  ```diff
       r = requests.get(
           f"https://api.github.com/repos/{GITHUB_REPO}/actions/jobs/{jobs[0]['id']}/logs",
           headers=GH, timeout=30, allow_redirects=True,
       )
  +    r.encoding = "utf-8"
       return r.text
  ```
- **是否已修**：**未修**，待人工核准（見待決事項 1）。改動範圍僅 1 行，風險極低，且已持續造成監測資料失真超過 30 天。

## 三、優化建議

### 建議 1（方向 A，依據問題 27 實測）：修正政府採購網地區判定被 `agency` 覆蓋的問題
- **依據**：09-24、09-25 連續 2 天推播基隆市案件（非雙北），累計已造成 2 次真實曝光。
- **做法**：見歷史報告（09-25）附上的 `OTHER_CITIES` 反向排除 diff。
- **預期效果**：堵住「機關雙北、資產跨縣市」這類全國性來源特有的誤判模式。

### 建議 2（方向 A，依據問題 28 實測）：blacklist 新增「投標單」「投標標價清單」
- **依據**：09-24 已有 1 筆真實推播為表單附件標題而非案名。
- **做法**：`GLOBAL_FILTER["blacklist"]`（`scraper.py` 頂部）新增上述兩詞。
- **預期效果**：從根本阻擋表單附件類噪音。

### 建議 3（方向 B，依據問題 26 實測）：土地銀行出租不動產來源建議移除
- **依據**：近 7 天 `notify` 總數為 0；本次核對 `state.json` 45 筆記錄樣本顯示 parser 實際抓到的是網銀系統維護公告與行銷頁，並非該站的出租不動產列表，屬「parser 對錯頁面」而非「篩選過嚴」。
- **做法**：確認該站是否有獨立的「出租不動產」頁面（與目前抓的頁面不同 URL），若無則建議直接移除此來源，避免每日浪費一次外部請求且汙染 `state.json`。
- **預期效果**：減少無效抓取與 state 檔案膨脹，不影響推播品質（本就 0 notify）。

### 建議 4（流程面，依據本次追蹤清單斷點觀察）：QA 報告應維持「延續問題編號＋累計天數」的固定格式，避免像問題 A（原問題 7）一樣在無修復記錄的情況下從報告中消失
- **依據**：`log_checker.py` 編碼問題於 09-09～09-22 被連續追蹤 14 天，09-23 起無任何 commit 變更卻不再出現在報告中，直到本次才重新發現，形同監測失效超過 30 天卻中途漏了 4 天以上未被提醒。
- **做法**：建議報告產生時，先讀取前一份報告「待決事項」清單，逐項確認是否已解決（有對應 commit）或仍待決，待決項目一律照抄延續，不可無故省略；只有明確標記「已解除」的項目才能移出清單。
- **預期效果**：避免高價值、低風險的修復建議（如本例僅需 1 行程式碼）因報告斷點而被人工遺忘超過一個月。
