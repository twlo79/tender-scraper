### 問題 4（延續，本次重新診斷出更精確的根本原因）：`daily_report.json` 30 天內從未成功解析出 `sources`

- **現象**：檢查 `daily_report.json` 全部 30 筆歷史紀錄，`sources` 欄位**無一天**非空、`total_new`／`total_pushed` **永遠是 0**——即使當天 `sent_log.json` 顯示確實有推播（如 08-24、08-26、08-28 皆有 1 筆 notify）。
  過去報告（08-23～08-28）認為根因是 `.github/workflows/log-check.yml` 缺 `actions: read` 權限、導致完全抓不到 log。本次重新檢查發現這個診斷**不完整**：
  1. 用 GitHub API 直接下載 `daily.yml` 最新 run 的原始 job log，內容格式完全正常（UTF-8），例如：`抓取：台北自來水處` 接著 `→ 共 4 筆，新增 0 筆，推播 0 筆`，與 `log_checker.py` 的正規表達式 `r"抓取：(.+?)\n.*?共\s*(\d+)\s*筆.*?新增\s*(\d+)\s*筆.*?推播\s*(\d+)\s*筆"` 完全吻合，理論上應該要能解析成功。
  2. `daily_report.json` 08-26 那筆的 `errors` 欄位確實抓到了內容（`GET å¤±æ https://esvc.fnp.gov.tw/...`），代表 `get_latest_log()` 那次**成功**從 GitHub 取回了真正的 job log 文字（否則不會有任何內容），但中文字全部變成了亂碼（`失敗` → `å¤±æ`），這是典型的「UTF-8 內容被誤判/退回為 ISO-8859-1 解碼」造成的亂碼。
  3. 對照 `log_checker.py:46-50`，抓取 job log 的 `requests.get(...)` **沒有**像 `scraper.py` 的 `get()` 函式一樣手動設定 `r.encoding`；而 GitHub Actions job log 下載連結（Azure Blob 簽章網址）回應的 `Content-Type: text/plain` 不含 `charset`，此時 `requests` 依 RFC 2616 預設值會把它解碼成 `ISO-8859-1`，導致所有中文（含用來比對的關鍵字「抓取：」）全部亂碼、regex 永遠比對不到，`sources` 因此永遠是 `{}`。
  4. 換言之：**log 抓取本身其實是成功的**（否則連亂碼後的 `WARNING`/`ERROR` 這類 ASCII 關鍵字也不會被抓到），真正卡住的是解碼這一步；`actions: read` 權限缺漏是否也是問題目前證據不足以確認（過去 30 天沒有任何一次回傳空字串或 API 錯誤訊息的跡象），優先順序應該放在編碼修正上。
- **定位**：`log_checker.py:46-50`（`get_latest_log()`，下載 job log 後未設定 `r.encoding`）。
- **建議修法**（比過去報告的 `actions: read` 修法更關鍵，建議優先套用）：
  ```diff
       r = requests.get(
           f"https://api.github.com/repos/{GITHUB_REPO}/actions/jobs/{jobs[0]['id']}/logs",
           headers=GH, timeout=30, allow_redirects=True,

  ```
- **是否已修**：未修。套用編碼修正後，建議人工手動 `workflow_dispatch` 觸發一次 `log-check.yml` 驗證 `daily_report.json` 是否能正確寫入 `sources`。

- **依據**：`passes_filters()` 對 `state.json` 全庫 830 筆重放，仍有 2 筆會通過現有篩選但屬非目標案件（廣告標租 1、停車類 1），且已有 2 次真實外洩紀錄；國營台鐵快取中另有 6 筆非雙北案件（新竹×5、桃園×1）目前雖已過期不會推播，但地區二次過濾缺漏是持續性風險。三組 diff 彼此不衝突，可一次套用。
- **做法**：套用「二、異常與處理」問題 2、3、5 的 diff。
- **預期效果**：排除已確認的誤報型態（廣告版位、停車、地區誤判），並讓 `SOURCES` 逐來源篩選設定真正生效。

### 建議 2（方向 A）：「土地銀行出租不動產」應優先修 parser 或考慮暫時下架

- **依據**：38 筆快取中 68%（26 筆）是網銀系統維護公告而非出租不動產公告，31 天 fetched=60、notify=0，是本次唯一被證實「抓到的內容完全不是目標案件類型」的來源（其他零推播來源快取內容經抽查仍是真實不動產案件，只是暫無新案）。
- **做法**：短期套用問題 7 的關鍵字排除過渡方案降低雜訊；中期需在有網路權限環境核對 `RentRealty` 頁面真正的公告 table selector 並重寫 `parse_landbank()`；若短期內無法核對，建議先暫停此來源（不列入每日抓取），避免長期消耗執行時間卻毫無產出。
- **預期效果**：避免每日執行浪費在抓取無效內容，且能更快看出是否應該投入資源修復或直接汰換此來源。

### 建議 3（方向 A）：「郵局房地產出租」有雙北真案件因標題未寫市名被地區篩選誤殺

- **依據**：22 筆快取中有 2 筆（9.1%）確定屬雙北：「內湖『那魯灣科技中心2樓』公開徵租」（內湖區）、「南港區『南港軟體園區一期E棟9樓』公開徵租」（南港區），標題僅寫行政區、未寫「台北」二字而被 `GLOBAL_FILTER["regions"]` 擋下。
- **做法**：在 `parse_post()` 內依標題出現的雙北專屬行政區關鍵字（內湖、南港、板橋、汐止等，須排除「中山」「中正」等全台同名區）額外標記 `agency`，而非直接把行政區名整批塞進 `GLOBAL_FILTER["regions"]`。需人工判斷雙北專屬區名清單，故列為待決事項而非直接提供 diff。
- **預期效果**：讓「郵局房地產出租」不再因標題慣例漏推雙北案件，同時避免引入新的地區誤判。

### 建議 4（方向 B）：長期零推播來源彙整

- **依據**：31 天累計 notify：台北市都發局 0（fetched 570）、農業部瑠公管理處 0（480）、台北市財政局 0（366）、國防部政治作戰局 0（209）、台北自來水處 0（87）、政府採購網 0（73）、國有財產署 1（68，且近 5 天全為 0）、土地銀行 0（60，見問題 7）。其中台北市都發局／台北市財政局／農業部瑠公管理處／國防部政治作戰局經抽查快取內容仍為真實雙北不動產案件，僅是近期無新案，判斷健康；政府採購網（問題 6）與土地銀行（問題 7）則有結構性 parser 問題證據；國有財產署（問題 1）已達異常門檻。
- **做法**：優先處理問題 1（國有財產署）與問題 7（土地銀行）；政府採購網建議下次比對時同步核對 table selector。
- **預期效果**：把「無新案」與「來源已經失效但看起來像沒新案」明確區分。
