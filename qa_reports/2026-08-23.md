### 問題 4（新發現，⚠️ 重要）：`log-check.yml` / `log_checker.py` 已失效超過 30 天，`daily_report.json` 完全不可信

- **現象**：`daily_report.json` 近 30 天（2026-07-24～08-22）**每一天**的 `sources` 皆為空字典、`total_new`/`total_pushed` 皆為 0，即使當天 `sent_log.json` 顯示有實際新增與推播（例如 08-21 `sent_log.json._summary` 為 `total_new=7, total_notify=1, line_pushed=true`，但同日 `daily_report.json` 卻記為 `total_new=0, total_pushed=0`）。
  - 已用 GitHub API 直接抓取 08-21 該次 `daily.yml` scrape job（job `96638718875`）的原始 log，確認 log 內容**完全符合** `log_checker.py` 的正則格式（`抓取：NAME` → `→ 共 X 筆，新增 Y 筆，推播 Z 筆`、`合計新增：N 筆 推播：M 筆`），並在本機以相同文字重放該正則，**可正確解析出 `total_new=7, total_pushed=1`**。
  - 同時查詢對應的 `log-check.yml` 執行（job `96663286035`），其 `python log_checker.py` 步驟僅耗時約 **2.6 秒**（03:56:52.03～03:56:54.68）即印出空結果並成功寫回 `daily_report.json`，執行過程無任何錯誤訊息，workflow 判定為 `success`。時間過短、且未拋例外，代表 `get_latest_log()` 確實拿到了「非空字串」但內容不是預期的 log 全文（否則 `if not log: sys.exit(1)` 會讓 job 失敗，但近 5 次 `log-check.yml` run 全數 `success`）。
  - **最可能原因**：`.github/workflows/log-check.yml` 的 `permissions:` 區塊只宣告了 `contents: write`，未宣告 `actions: read`。GitHub Actions 規則是「一旦宣告 `permissions:`，未列出的權限一律降為 `none`」，因此該 job 的 `GITHUB_TOKEN` 呼叫 `GET /actions/workflows/daily.yml/runs`、`/actions/runs/{id}/jobs`、`/actions/jobs/{id}/logs` 這三個 Actions API 極可能被 403 拒絕，回傳簡短的 JSON 錯誤訊息（而非真正的 log 全文）。`get_latest_log()` 沒有檢查 HTTP 狀態碼，直接把這段錯誤 JSON 當成 log 文字餵給 `parse_log()`，導致正則全部落空但不拋錯，靜默寫入全零報告。
- **定位**：`.github/workflows/log-check.yml`（`permissions:` 區塊）；次要定位 `log_checker.py:get_latest_log()`（缺少狀態碼檢查）。
- **建議修法**：
  ```diff
   permissions:
     contents: write
  +  actions: read
  ```
  並在 `log_checker.py` 加上狀態碼檢查以避免未來再次靜默失敗：
  ```diff
       r = requests.get(
           f"https://api.github.com/repos/{GITHUB_REPO}/actions/workflows/daily.yml/runs?per_page=2",
           headers=GH, timeout=20,
       )
  +    if r.status_code != 200:
  +        print(f"❌ 無法取得 workflow runs：HTTP {r.status_code} {r.text[:200]}")
  +        return ""
       runs = r.json().get("workflow_runs", [])
  ```
  （`jobs` 與 `logs` 兩處 API 呼叫建議比照加上相同檢查。）
- **是否已修**：未修。**建議套用 `permissions` 修正後，手動 `workflow_dispatch` 觸發一次 `log-check.yml`，確認 `daily_report.json` 當天條目的 `sources` 不再是空字典，作為驗證。**
- **影響評估**：不影響爬蟲本身抓取／推播（`daily.yml` 與 `sent_log.json` 皆正常），但代表過去 30 天所有依賴 `daily_report.json` 做每日健康判斷的機制形同虛設；本報告改以 GitHub API 直讀 `sent_log.json` 與 workflow run 狀態繞過此問題，故不影響本次監測結論的正確性。

### 問題 5（新發現）：`SOURCES` 中各來源自訂的 `whitelist`/`blacklist`/`regions` 設定從未生效

- **現象**：`scraper.py` 的 `SOURCES` 清單為每個來源都定義了個別的 `whitelist`/`blacklist`/`regions`（例如 Google Alerts 的 `regions` 額外包含 `"gov.tw"`，註解寫「讓全台政府公告通過」；國防部政治作戰局的 `whitelist` 額外包含 `"土地"`, `"眷村"`）。但實際套用篩選的 `passes_filters(item)`（`scraper.py:796-814`）**只讀取 `GLOBAL_FILTER`**，完全沒有讀取 `item` 所屬 `src` 的個別設定，這些逐來源設定是死碼，從未被執行。

- **定位**：`scraper.py:796-814`（`passes_filters`）與其呼叫處 `scraper.py:1151`。
- **建議修法**（採「聯集」而非「覆蓋」，確保現有行為不倒退，僅補上原本設計要放行的項目）：
  ```diff
  -def passes_filters(item: dict) -> bool:
  +def passes_filters(item: dict, src: dict | None = None) -> bool:
       """套用 GLOBAL_FILTER 的白名單、黑名單、地區篩選（所有來源共用，可被單一來源設定擴充）。"""
       title  = item.get("title", "")
       agency = item.get("agency", "")
       text   = title + agency
  +    src = src or {}

  -    regions = GLOBAL_FILTER.get("regions", [])
  +    regions = GLOBAL_FILTER.get("regions", []) + src.get("regions", [])
       if regions and not any(k in text for k in regions):
           return False

  -    whitelist = GLOBAL_FILTER.get("whitelist", [])
  +    whitelist = GLOBAL_FILTER.get("whitelist", []) + src.get("whitelist", [])
       if whitelist and not any(k in title for k in whitelist):
           return False

       blacklist = GLOBAL_FILTER.get("blacklist", [])
       if blacklist and any(k in title for k in blacklist):
           return False

       return True
  ```
  並將呼叫處（`scraper.py:1151` 附近）由 `passes_filters(i)` 改為 `passes_filters(i, src)`。
