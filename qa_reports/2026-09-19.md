### 問題 13（新增）：`get()` 對非 2xx HTTP 回應的判斷式會誤判為「無回應」，且完全不留 log——已造成國防部政治作戰局今日靜默失效

- **現象**：今日 production log 中，國防部政治作戰局的區塊只有：

  ```python

  ```
  而 `get()`（`scraper.py:99-106`）僅在 `requests` 拋出例外時才回傳 `None` 並 log `GET 失敗`；若連線成功但站方回應非 2xx（如 403/404/503），`get()` 會照常回傳該 `Response` 物件（不是 `None`），但 Python `requests.Response.__bool__` 定義為 `self.ok`（`status_code < 400`），因此 `if not r:` 在「連線失敗（r is None）」與「連線成功但站方回應錯誤碼」兩種完全不同的情況下都會為真，且後者由於沒有拋出例外，**不會**觸發 `get()` 裡的 `log.warning`，導致這種情況在 log 中完全無跡可尋。今日該來源 fetched 從連續 9 天（09-10～09-18）穩定的 11 筆驟降為 0，且缺少上述 log 特徵，與「站方回應非 2xx 被靜默吞噬」的模式完全吻合，非「查無資料」（若查無資料，`parse_gpwd()` 會先跑完 `soup.select()` 迴圈得到空列表、再嘗試 Claude fallback，最終仍會印出「0 筆」那行 log，如同今日的政府採購網、國有財產署）。

## 三、優化建議

### 建議 1（新增，依據問題 14，優先度高——直接影響使用者收到的推播品質）：新增跨來源標題正規化去重，避免同案重複推播

- **依據**：今日 3 筆推播中，3 筆（100%）其實是同一件案子，分別由「農業部 瑠公管理處」自有 parser 與「Google Alerts」（2 個不同鏡像網址）各自觸發；過去 7 天（09-13～09-18）逐日核對皆無此類跨來源標題重複，今日是首次發生，代表這不是罕見狀況、而是「只要同一案件同時被官方來源與 Google Alerts 收錄」就會發生的結構性風險。
- **做法**：套用問題 14 的 diff，在 `main()` 迴圈跑完所有來源後、推播前加入以標題正規化（去除所有空白）為 key 的跨來源去重，依 `SOURCES` 宣告順序保留較前面（通常是官方自有來源）的那一筆。
- **預期效果**：消除同一案件被重複推播給訂閱者的體驗問題，且不影響真正不同案件的正常推播。

### 建議 2（新增，依據問題 13）：修正 `get()` 對非 2xx 回應的靜默吞噬，讓來源異常有 log 可查

- **依據**：國防部政治作戰局今日 fetched 從連續 9 天（09-10～09-18）穩定的 11 筆驟降為 0（跌幅 100%），但 production log 中完全沒有任何診斷線索（既非「GET 失敗」例外、也沒有「0 筆」的正常空結果 log）；追查發現 `scraper.py:578` 的 `if not r:` 因 `requests.Response.__bool__` 對非 2xx 回應回傳 `False`，會把「站方拒絕/出錯」誤判為「無回應」且完全不留 log。此寫法在 repo 中共出現 11 處（涵蓋幾乎所有來源的 parser），代表這不只是國防部政治作戰局單一來源的問題，而是整個監測系統對「來源被封鎖/改版導致 HTTP 錯誤」這一類故障普遍缺乏可觀測性。
- **做法**：套用問題 13 的 diff，僅需修改 `get()` 這一個函式（單一改點），讓所有 11 處呼叫點在遇到非 2xx 回應時自動留下 `HTTP {status_code}` 的 log，不需逐一修改各 parser。
- **預期效果**：未來任一來源被目標網站擋下（403/503 等）時，QA 能直接從 log 判讀具體原因，不必每次都懷疑「是否為真實查無資料」再花時間人工排查；也能讓問題 12（國有財產署）、問題 2（政府採購網）之類的長期斷線問題在未來若轉變為 HTTP 錯誤時被更快發現。
