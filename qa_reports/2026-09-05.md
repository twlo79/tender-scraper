### 問題 7（新增）：國有財產署「115年第17批」同一案件重複推播（09-01、09-05 各推一次）

- **現象**：`sent_log.json` 中「【招標公告】北區分署 115年第17批 招標公告 公告:115年08月31日 開標:115年09月15日」於 `2026-09-01 01:30` 與 `2026-09-05 01:30` 各被標記 `notify=1` 並實際推播一次，是同一案件（同公告日期、同開標日期、同 msgId）。
- **定位**：檢視 `state.json` 的 `國有財產署` 陣列，此案存在**兩筆重複紀錄**：
  ```json
  {"title": "【招標公告】北區分署 115年第17批...", "date": "115年08月31日", "url": ".../showInfomation?msgId=cfb240db54e5460c8b987bba9253b9db"}
  {"id": "cfb240db54e5460c8b987bba9253b9db", "title": "【招標公告】北區分署 115年第17批...", "date": "115年08月31日", "url": ".../showInfomation?msgId=cfb240db54e5460c8b987bba9253b9db"}
  ```
  兩筆的 `title`／`date`／`url` 完全相同，只差在第一筆缺少 `id` 欄位。`item_key()`（`scraper.py:979-984`）以 `id+title+date+url` 組合去重鍵，`item.get("id","")` 對缺 `id` 的舊紀錄與新抓到、已含 `id` 的項目算出**不同的 key**，`find_new_items()` 因而判定為「新項目」而重複推播，且把兩種 key 的版本都留在 `state.json` 裡（永久重複，往後只要標題/日期/url 再次完全相符但 id 存在與否不一致，仍會再次誤判為新案）。根因研判是 `國有財產署` 是目前唯一真的會填入 `id`（msgId）的來源，而某次抓取這批公告時 `id` 擷取失敗或尚未加入 `id` 欄位邏輯，留下缺 `id` 的舊紀錄，之後正常擷取到 `id` 後就與舊紀錄對不上。
- **建議修法**：`find_new_items()` 判斷「是否已存在」時，改成同時檢查含 `id` 與不含 `id` 兩種 key，避免歷史缺 `id` 紀錄被誤判為新案：
  ```diff
   def find_new_items(name: str, items: list[dict], state: dict) -> list[dict]:
       existing = state.get(name, [])
       seen = {_entry_key(e) for e in existing}
  +    # 舊紀錄可能缺少 id 欄位（如國有財產署曾發生），只用 title+date+url 做第二層比對，
  +    # 避免同一案件因 id 有無不一致而被誤判為新案、重複推播。
  +    def _no_id_key(d: dict) -> str:
  +        return re.sub(r"\s+", "", "|".join((d.get("title", ""), d.get("date", ""), d.get("url", ""))))
  +    seen_no_id = {_no_id_key(e) for e in existing if isinstance(e, dict)}
       new  = [i for i in items if item_key(i) not in seen]
  +    new  = [i for i in new if _no_id_key(i) not in seen_no_id]
       ...
  ```
  另需注意：此修法生效後，`state.json` 裡既有的重複紀錄本身不會自動清除（規則禁止本次直接修改 `state.json`），需要人工決定是否手動去重，或讓其自然留存（不影響未來判斷，只是 300 筆上限的快取多佔 1 筆）。
- **是否已修**：未修（新發現，待核准）。

## 三、優化建議

### 建議 1（方向 A）：問題 7（國有財產署重複推播）與問題 1（國營台鐵零過濾）應優先套用

- **依據**：問題 7 是本次新確認的真實重複推播（同一案件兩次進使用者的 LINE），問題 1 是唯一「新項目 100% 直接推播、地區篩選零效果」的來源，兩者都已造成過真實的錯誤通知（問題 1：09-01 基隆、09-03 桃園；問題 7：09-01、09-05 重複同一案）。
- **做法**：套用問題 7 的 `find_new_items()` 雙重 key 檢查 + 問題 1 的 `parse_tra()` 地點判定 diff；套用後需以 `dry_run_all_regions.py --debug --source 國營台鐵` 及 `--source 國有財產署` 比對修法前後筆數（目前環境對外連線全數 proxy 403，需於有網路權限環境驗證）。
- **預期效果**：國營台鐵不再誤放非雙北案件；國有財產署不再對同一案件重複推播。

### 建議 2（方向 A）：Google Alerts「gov.tw 全台放行」死碼是潛在的假陰性來源，建議評估修復範圍

- **依據**：`scraper.py:803` 的設計意圖是讓 `.gov.tw` 網域的政府公告即使標題未寫地名也能通過地區篩選，但因 `SOURCES` 逐來源設定（問題 6）從未被 `passes_filters()` 讀取，此邏輯完全沒有生效過。Google Alerts 7 天內 `fetched=24`、`new=23`、`notify=2`，notify/new 比例僅 8.7%，其餘 21 筆新項目中有多少是因為標題沒寫「台北/新北」而被地區篩擋下、而非因為不含租賃關鍵字被白名單擋下，目前無法在此環境連線查證（需要 `dry_run_all_regions.py --non-taipei` 實測，本環境對 `google.com` 亦為 proxy 403）。
- **做法**：先在有網路權限的環境跑 `dry_run_all_regions.py --non-taipei --source "Google Alerts"`，統計有多少筆是「標題含雙北地名但被其他條件擋下」vs.「案件確實在雙北但標題沒寫地名、只能靠 gov.tw 網域判斷」，再決定問題 6 的修法範圍（全面套用 vs. 只修 Google Alerts 這一種情境）。
- **預期效果**：釐清是否有雙北案件因標題未寫地名而被誤殺，避免修法範圍過大或過小。
