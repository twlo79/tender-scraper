### 問題 10（新發現）：國有財產署 `skip_global_filter=True` 讓 4 個分類頁完全不受內容篩選，今日已造成 1 筆真實漏網推播

- **現象**：今日 LINE 實際推播了「【招標公告】北區分署 115年第17批 招標公告 公告:115年08月31日 開標:115年09月15日」。`qa_report.py --days 7` 明確標記此筆「不含任何白名單關鍵字」。標題本身也只是「分類＋批號＋日期」的彙總列，看不出實際案件內容是不是不動產租賃。
- **定位**：
  - `scraper.py:741-746`（`SOURCES` 中國有財產署條目 `"skip_global_filter": True`）
  - `scraper.py:328-387`（`parse_fnp()`，抓取 4 個類別頁：招標公告／地上權設定／**停車場**／創業租賃，只用「單位＝北區分署」過濾，完全不檢查內容類型）
  - 標題組成 `title = f"【{page['cat']}】{unit} {year}年第{batch}批 {kind} 公告:{pub_dt} 開標:{open_dt}"`（`scraper.py:380`）——`kind` 欄位若網站沒填會直接退回 `page['cat']`（即分類名稱本身），今日推播的項目正是這種情況。
  - 更嚴重的是：`FNP_PAGES` 4 個分類裡的「停車場」本身就是業務背景明確排除的類型（「停車場…都不是目標」），但因為 `skip_global_filter=True`，即使真的抓到停車場項目也會直接推播，完全繞過黑名單。
- **為何當初設 `skip_global_filter`**：程式碼註解寫「標題為組合字串，已在 parser 篩北區分署」——這只處理了「地區」這一層，沒處理「內容類型」這一層，兩者被誤認為同一件事。
- **建議修法**（兩步，互相獨立，可分開套用）：

  1）移除「停車場」分類頁（業務背景明確排除，風險最高、最無爭議）：
  ```diff
   FNP_PAGES = [
       {"cat": "招標公告",   "url": "https://esvc.fnp.gov.tw/rtMsg?svcId=5eafac8df8c649ba9cf62a591e44223c"},
       {"cat": "地上權設定", "url": "https://esvc.fnp.gov.tw/tenderSetSuperficies?svcId=f6c87d65ebc84e988b4d245777d83a81"},
  -    {"cat": "停車場",     "url": "https://esvc.fnp.gov.tw/parkingMsg?svcId=a211eb824d6841d598fc784fb44ba962"},
       {"cat": "創業租賃",   "url": "https://esvc.fnp.gov.tw/crtMsg?svcId=ecc2694bdf6144e298053cb2a9f2460f"},
   ]
  ```

  2）拿掉 `skip_global_filter`，改用一般 GLOBAL_FILTER 白名單／黑名單把關（「創業租賃」分類標題含「租賃」可通過白名單；「招標公告」「地上權設定」分類因標題不含白名單詞會被正確擋下，行為上等於今天這筆漏網會被自動擋掉）：
  ```diff
       {
           "name": "國有財產署",
           "fn": parse_fnp,
           "whitelist": [], "blacklist": [], "regions": [],
  -        "skip_global_filter": True,  # 標題為組合字串，已在 parser 篩北區分署
       },
  ```
  同時建議在 GLOBAL_FILTER 黑名單補上「停車場」作為保險（即使分類頁被移除，未來其他來源標題含「停車場」仍應排除）：
  ```diff
       "blacklist": [
           "開標結果",
  -        "自動販賣機", "場地短期出租", "機械類標租", "共享雨傘",
  +        "自動販賣機", "場地短期出租", "機械類標租", "共享雨傘", "停車場",
           "新建工程", "統包工程", "物業管理", "專案管理", "保險",
           "清洗作業", "鑄鐵直管", "延性鑄鐵", "塗裝", "管線",
  ```

### 問題 11（新發現）：安幸 ERP 匯入自 08-28 上線以來，今日第一次真正有內容可送，就失敗

- **現象**：今日 job log：
  ```
  01:31:27 WARNING   ⚠ ERP 匯入異常（不影響 LINE 推播）：Invalid leading whitespace, reserved character(s), or return character(s) in header value: '***\n'
  ```
  `push_to_anxing()` 是 08-28 16:45 commit `b504d6c` 新增的功能。追查歷史：08-28～08-31 每次執行的 `notify` 都是 0 筆，`push_to_anxing()` 內 `if not records: return`（`scraper.py:1148-1150`）直接跳過，從未真正打過 API；今天是新增此功能後第一次有 `notify>0`，一打就因為 header 值含換行字元而失敗。也就是說這個整合功能實際上**從未成功執行過一次**。
- **定位**：`scraper.py:1131-1132`
  ```python
  url = os.getenv("ANXING_URL", "")
  key = os.getenv("ANXING_KEY", "")
  ```
  `requests` 對 header 值的驗證不接受結尾換行字元，錯誤訊息 `'***\n'` 顯示是 `ANXING_KEY`（或 `ANXING_URL`）這兩個 GitHub Secrets 中，至少有一個結尾多了 `\n`，最常見成因是設定 Secret 時用 `echo`／複製貼上帶了換行的內容。
- **建議修法**（程式端加防禦性 `.strip()`，屬於低風險、不影響任何現有行為的修改，但**無法取代**修正 Secret 本身，因為若 Secret 值中段也混有其他非法字元，`.strip()` 救不了，仍需去 GitHub repo Settings → Secrets 重新設定 `ANXING_KEY`／`ANXING_URL` 兩者）：
  ```diff
       url = os.getenv("ANXING_URL", "")
       key = os.getenv("ANXING_KEY", "")
  +    url = url.strip()
  +    key = key.strip()
  ```
- **是否已修**：未修。此為新上線功能的首次故障，需要人工去 GitHub Secrets 重新設定 `ANXING_KEY`（可能也包含 `ANXING_URL`）後才能真正驗證（無法在本 QA 環境重現，因為看不到 Secret 明文）。
