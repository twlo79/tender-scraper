## 二、異常與處理

### 問題 1：多個來源透過 Claude fallback 解析時，url 空白 + 網站導覽文字被誤抓成標案
- **現象**：`state.json` 顯示「國家住宅及都市更新中心」的項目中，有「會員中心」「委員名單」「加入會員」這類明顯是網站導覽選單、而非標案名稱的項目被存入。同時該來源及都發局／政治作戰局／教育部學產基金／政府採購網的 `url` 欄位分別有 47%～100% 是空字串。
- **定位**：
  1. `scraper.py:113` 定義了 `_is_junk(item)` 過濾器（比對「請至」「查詢頁面」「本頁面」「回首頁」等導覽文字關鍵字），但全檔搜尋只有這一處定義，**從未在任何地方被呼叫**——是個沒接上的死代碼，Claude fallback 抓到的垃圾項目完全沒被它擋下。
  2. `scraper.py:675-699` 的 `parse_with_claude_fallback()` 把 `soup.get_text("\n")[:8000]`（**純文字，已去除所有 `<a href>`**）餵給 Claude，但 prompt（`PARSE_PROMPT`）仍要求 Claude 回傳 `"url"` 欄位——輸入內容本身就不含連結資訊，Claude 只能回傳空字串或亂猜，這是多個來源 url 大量空白的結構性原因。這些空白 url 之後在 `build_line_messages()`（`scraper.py:1081-1083`）會 fallback 成該來源的列表頁網址，而非個別公告頁。
- **建議修法**：
  1. 在 `parse_with_claude_fallback()` 套用既有的 `_is_junk`：
     ```diff
              raw = re.sub(r"^```(?:json)?|```$", "", raw, flags=re.MULTILINE).strip()
              items = json.loads(raw)
     +        items = [it for it in items if isinstance(it, dict) and not _is_junk(it)]
              for item in items:
                  u = item.get("url", "")
     ```
  2. 讓 Claude fallback 拿得到連結，把餵給 Claude 的內容從純文字改成保留連結的簡化格式：
     ```diff
     +def _serialize_links(soup) -> str:
     +    """保留 <a href> 的簡化文字表示，供 Claude fallback 解析 url 用。"""
     +    lines = []
     +    for a in soup.find_all("a", href=True):
     +        text = a.get_text(strip=True)
     +        if text:
     +            lines.append(f"{text}\t[[{a['href']}]]")
     +    return "\n".join(lines)
     +
      PARSE_PROMPT = """你是政府標案資料擷取助手。
      以下是某政府機關「標案/招標/出租」頁面的文字。
      找出所有標案或出租公告，回傳 JSON 陣列：
      [{{"title":"標案名稱","date":"日期或空字串","url":"連結或空字串"}}]
     +每行格式為「文字 [[網址]]」，url 請直接取 [[ ]] 內的原始值，不要自行編造。
      只回傳 JSON，無說明文字。若無標案回傳 []。
      頁面文字：\n{text}"""
     ```
     並將呼叫端例如 `scraper.py:554`、`323`、`452`、`510`、`587` 的 `soup.get_text("\n")[:8000]` 改成 `_serialize_links(soup)[:8000]`。
- **是否已修**：未修（依規則本次僅定位，不自動改程式碼；且 sandbox 無法連線驗證，修改後需用 `dry_run_all_regions.py --debug --source <來源>` 在有網路權限環境驗證 url 是否正確帶出）

### 問題 2：台北自來水處 date 欄位 100% 空白，日期窗篩選失效
- **現象**：`state.json` 中「台北自來水處」累積的 55 筆項目，`date` 欄位全數（55/55）為空字串，但同一 parser 的 `title` 欄位是正常的（55/55 有標題）。
- **定位**：`scraper.py:128-161` `parse_taipei_water()`。標題抓取有 4 層 fallback（3 個 `data-title` 候選 key + 「任一含 `<a>` 的 td」保底），但日期只查：
  ```python
  date_td = td_map.get("公告日期") or td_map.get("發布日期") or td_map.get("日期")
  ```
  沒有任何 fallback。若目前頁面實際的 `data-title` 屬性不是這三個字串之一，`date_td` 永遠是 `None`，`dt` 永遠是空字串。因為 `is_within_date_window()`（`scraper.py:1009-1021`）在日期無法解析時會直接放行，這個來源目前完全不受 `DATE_WINDOW_DAYS=10` 限制——舊公告一樣會被視為「在窗口內」。
- **建議修法**：加入正則掃描任一 td 文字取得日期的保底邏輯：
  ```diff
       date_td = td_map.get("公告日期") or td_map.get("發布日期") or td_map.get("日期")
       dt = date_td.get_text(strip=True) if date_td else ""
  +    if not dt:
  +        for td in tds:
  +            txt = td.get_text(strip=True)
  +            if re.search(r"\d{2,4}[/.\-年]\d{1,2}[/.\-月]\d{1,2}", txt):
  +                dt = txt
  +                break
  ```
- **是否已修**：未修（需先在有網路權限環境用 `dry_run_all_regions.py --debug --source 台北自來水處` 確認實際 `data-title` 屬性名稱，再套用對應 diff；本次 sandbox 對外連線一律 `EGRESS_BLOCKED`，無法即時驗證）

## 三、優化建議

### 建議 1：blacklist 尚未涵蓋「停車」類關鍵字，屬預防性風險
- **依據**：對 `state.json` 全庫掃描（跨全部 13 來源）找到 27 筆標題含「停車」的項目，其中至少 8 筆是雙北轄區、且會通過現有白名單（含「標租」）與地區篩選（含「台北」/「新北」）的停車場/停車位案件，例如台北市財政局來源：
  - 「公開標租臺北市內湖區康寧段四小段452-2地號市有土地作單一停車位使用案」
  - 「公開標租新北市板橋區江子翠段第二崁小段189-5地號臺北市有土地作臨時路外停車場使用案」
  - 「公開標租新北市板橋區永翠段1地號臺北市有土地作臨時平面停車場使用」

  目前 `GLOBAL_FILTER["blacklist"]` 只有「自動販賣機」「場地短期出租」「機械類標租」等詞，沒有任何「停車」相關詞。本週這些項目公告日期不在 10 天窗口內所以尚未被誤推，但只要日後有新的同類公告落在窗口內，就會被誤判為目標案件推播出去（業務目標明確排除停車場）。
- **做法**：在 `GLOBAL_FILTER["blacklist"]` 加入具體詞組（避免用過於寬鬆的「停車」單字，以免誤傷含「停車場旁」等描述的正常案件；目前抓到的實例都是「XX停車位使用」「XX停車場使用」「停車場經營」等明確措辭）：
  ```diff
       "blacklist": [
           "開標結果",
           "自動販賣機", "場地短期出租", "機械類標租", "共享雨傘",
  +        "停車位使用", "停車場使用", "停車場經營", "停車場委託經營",
           "新建工程", "統包工程", "物業管理", "專案管理", "保險",
           "清洗作業", "鑄鐵直管", "延性鑄鐵", "塗裝", "管線",
           "財物採購", "勞務採購",
       ],
  ```
- **預期效果**：排除已在資料中發現的 8+ 筆停車類假陽性風險案件，避免未來日期進入窗口後被誤推。

### 建議 2：大部分來源 7 天 notify=0，需區分「本週剛好沒新案」vs「篩選過嚴」

  抽查這些來源的樣本標題（如瑠公管理處「115年度第2批農田水利非事業用不動產公開標租案」、財政局「公開標租臺北市松山區南京東路...市有不動產」），日期橫跨民國109~115年，顯示這些頁面是**長期累積的歷史公告列表**，而非「本週新公告」列表——`new=0` 代表這些項目本來就在 `state.json` 裡（之前已抓過/已判斷過），並非本週篩選漏推。這是來源性質使然（公有不動產標租本來就不是天天發生），不是白名單過嚴的證據。

  例外是台北自來水處與政府採購網：各有 1 筆「新」項目但仍 0 推播，代表確實有東西被篩選層擋下，值得個別追查（可能是黑名單或日期窗，需配合問題 2 的 date 欄位 bug 一併排查）。
- **做法**：
  - 「歷史累積型」來源（瑠公管理處/財政局/國防部政治作戰局/都市更新中心/國有財產署/都發局）本質正常，**不建議調整或移除**，僅需維持現有監測頻率。

- **預期效果**：避免依「7 天 notify=0」片面判斷來源健康度不佳而誤刪有效來源；同時鎖定 2 筆真正需要追查的個案。
